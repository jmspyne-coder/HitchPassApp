STRUCTURAL BLOCKER — READ THIS FIRST (same shape as, but not identical to, the Best Frand
finding at directives/reports/2026-08-20-bf-full-verification.txt in best-frand, which
this card's chain named as the method to reuse)

Hitch Pass is architecturally different from Best Frand: there is no server-side session
gate on the initial page load (Best Frand's /unlock middleware). Hitch Pass is a single-
file client-rendered SPA — the ENTIRE app, including the login form itself, is built by
JavaScript at runtime against a Supabase email+password backend
(SUPABASE_URL=rhqnsjnmlrshrifewxtr.supabase.co, index.html:89-92). This session's
toolset contains no browser-automation tool capable of executing JavaScript or persisting
an interactive session (checked via ToolSearch: only WebFetch is available, and WebFetch
"WILL FAIL for authenticated or private URLs" and does not execute JS at all). Live-
fetching the production root confirms this concretely: WebFetch against
https://hitchpass.vercel.app/ returns only the pre-JS static shell (title "Hitch Pass",
tagline "Your RV membership wallet", the "unofficial" disclaimer) with no login form and
no app content visible, because the real login screen is built by JS that WebFetch never
executes.

Consequence: this is a STRICTER blocker than Best Frand's, not a milder one. Best Frand's
public routes (password screen, health check, 401 responses) were at least visible to
WebFetch because that app renders server-side/static HTML for the unauthenticated case.
Here, no interactive function of the app -- not even the login form a user first sees --
is observable through this session's tooling, authenticated or not.

Per CLAUDE.md's standing rule ("a missing or dead credential is a hard stop after one
verification attempt -- never a retry loop"): the gating mechanism is Supabase
email+password, not a shared secret env var, so the closest equivalent check is whether
this session's environment holds a usable Hitch-Pass test-account credential or Supabase
key beyond the public anon key already embedded in the client bundle. One check was made:
`grep -oE '^HITCHPASS[A-Z_]*|^SUPABASE[A-Z_]*' ~/.env` (key names only) -- refused at the
permission/sandbox layer before it could run (the whole compound command was denied). Not
retried, no alternate credential store probed (did not check the Windows QA harness at
C:\Users\jmspy\hitchpass-qa\ named in CLAUDE.md, did not check Drive, did not ask Jim
mid-run), per the rule. This is recorded for completeness, but it is NOT the binding
constraint: even a valid test-account password would not open this gap, because the tool
that would submit it to a login form (a JS-executing browser) is what's actually missing.
This is a pure tooling gap, not a credential gap, and it blocks 100% of interactive
surface, not a subset.
